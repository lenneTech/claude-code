# lenne.Tech Angular Frontend Development

The Angular line of the stack: an Angular 22 app (template `ng-base-starter`) on `@lenne.tech/ng-base`, against the
same `nest-server` backend as the Nuxt line. Routes, pages, UX rules and the backend contract are the Nuxt
template's; the framework idioms are Angular's.

## Read first: the app's own CLAUDE.md

The app's `CLAUDE.md` (from ng-base-starter) carries the Angular CLI's 36 official rules, kept verbatim from
`ng new --ai-config` with their source line, and below them the stack's additions. Those files are the rules;
this skill does not repeat or reword them. Where a project has no such file, the rules are what
`ng new --ai-config=claude-code` writes for the pinned Angular CLI version. Run `pnpm run check:baseline` after every
`ng update`: deviations from a fresh `ng new` are allowed only as listed in `scripts/check-angular-baseline.mjs`.

## Gotchas

- **Reference ng-base by package and entry point, never by file path.** Import `@lenne.tech/ng-base`,
  `@lenne.tech/ng-base/auth`, `.../auth/provide`, `.../ui`, `.../ui/provide`, `.../files`, `.../files/ui`,
  `.../share`, `.../ai`, `.../sync`, `.../server`, `.../testing`, `.../utils`. The same import works in npm and
  vendor mode (`tsconfig` maps the specifiers onto `src/core/`), and the library's internal layout is not a
  contract. Entry points you do not import are not bundled.
- **Per-call state is an `inject…()` function, not a composable or a service instance you construct.**
  `injectLtTusUpload()`, `injectLtAiChat()`, `injectLtOfflineSync()` run in an injection context (a field
  initializer or a constructor); shared state lives in root services (`LtAuthService`, `LtAuthStore`).
- **Keep Better Auth out of the initial bundle.** Shells and guards import from `@lenne.tech/ng-base/auth/provide`
  (`provideLtAuth()`, `ltAuthInterceptor`, `ltAuthGuard`, `ltGuestGuard()`, `ltRoleGuard()`,
  `ltSystemSetupGuard`, `LtAuthStore`); `LtAuthService` from `/auth` belongs on the pages that sign in, register,
  verify 2FA or manage passkeys. Passkeys need no `@better-auth/passkey`. UI providers come from
  `@lenne.tech/ng-base/ui/provide`, the toaster renders in a `@defer` block, and `provideLtUiOverlayDefaults()` goes
  into the layouts' providers, not `app.config.ts`.
- **hey-api resources stay idle without an options factory.** A generated `xResource()` without arguments never
  fires: write `xResource(() => ({}))`. Resources are generated for POST and DELETE too; use resources for GET only,
  and the SDK or `…Request()` functions for mutations. `provideHeyApiClient` lives in `api-client/client/client.gen.ts`,
  not in the barrel. `src/api-client/` is generated by `pnpm run generate-types` and never edited by hand; a missing
  type is fixed in the API.
- **`generate-types` needs a running API and refuses to guess it:** `NG_API_URL` from the shell or
  `<repo-root>/.lt-dev/.env` (written by `lt dev up`), otherwise it exits. Never add a fallback URL.
- **Runtime config is `NG_*`, read per request, nothing baked in.** `inject(LT_RUNTIME_CONFIG)` and
  `LtApiUrlService` (server: `NG_API_URL`, browser: `NG_PUBLIC_API_URL` or the `/api` proxy). Never read
  `process.env` in app code and never add `environment.ts` files: one image runs on every stage. `NG_API_URL`
  never reaches the browser.
- **SSR: no browser globals on the server.** Inject `DOCUMENT`, check `isPlatformBrowser`, or use
  `afterNextRender`. Redirect and callback URLs are absolute and built from `NG_PUBLIC_SITE_URL`, never from
  `location` on the server. Route guards read the client-writable `lt-auth-state` cookie: UI gates only, the API
  authorizes. Typed input survives hydration through ng-base's `preHydrationInput` (on by default).
- **Ports are part of the backend contract:** API 3000, app 3001. Another app port fails 2FA and passkeys with
  `403 INVALID_ORIGIN`; `pnpm run dev` refuses a busy port instead of moving. Under `lt dev up` use the URLs it
  prints (`https://<slug>.localhost`).
- **UI comes from `@lenne.tech/ng-base/ui`, not from Nuxt UI:** the Spartan-based Helm components (`HlmButton`,
  `HlmDialog`, `HlmInput` …) plus the lt components (`LtFormField`, `LtTextField`, `LtSelect`, `LtPageCard`,
  `LtDataView`, `LtConfirmDialog` …). Dialogs open programmatically through `LtOverlayService` (`open()`, `confirm()`;
  the opened component reads `injectLtOverlayData()`), the counterpart of `useOverlay()`. Tailwind utilities and
  semantic tokens only (`bg-primary`, `text-muted`), no component style files; a theme override goes into
  `src/styles.css` after the ng-base imports.
- **Styles cost budget.** `src/styles.css` imports ng-base's `ui/styles/core.css` plus one
  `ui/styles/components/<name>.css` per component the templates use, not the full `theme.css`. A new component
  means a new import (vendored app: `./core/ui/styles/…`, the package form fails `ng build` there); the starter's `tests/unit/styles-contract.test.ts` names a missing one. The CLI budgets in
  `angular.json` apply and are never raised to make a build pass.
- **Testing an unreleased ng-base is an injected `file:` dependency, never `pnpm link`:**
  `"@lenne.tech/ng-base": "file:../ng-base/dist/ng-base"` plus `dependenciesMeta.injected`, and `pnpm install`
  after every ng-base build. A linked `dist` runs two Angular copies and SSR fails with `NG0203`. Such a pin never
  ships (`pnpm run check:release` refuses it).
- **The Angular CLI MCP is the project's own CLI** (`npx ng mcp` from the app, the pinned version), never
  `npx @angular/cli@latest mcp`: it answers best practices and documentation for the version the app runs.
- **UI language and copy as in the Nuxt line:** detect the language from the project, never bulk-translate; UI text
  the task did not spell out follows the `unslop` rules.

## Framework Mode

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/detect-frontend.sh"    # frontend: angular · mode: npm | vendor · core: ...
```

- **npm mode:** `@lenne.tech/ng-base` is pinned exactly in `dependencies`; read the library from
  `node_modules/@lenne.tech/ng-base` (its `README.md` lists the entry points).
- **vendor mode:** the library is project code in `src/core/` with `VENDOR.md`. Edit it only for changes useful
  to every consumer; see the `ng-base-core-vendoring` skill, `/lt-dev:frontend:update-ng-base-core` and
  `/lt-dev:frontend:contribute-ng-base-core`.

## Authentication

The Nuxt template's auth rules carry over one to one (the app's CLAUDE.md lists them): errors through the error
translation (`#LTNS_xxxx`), Better Auth errors classified by `error.code`, passwords SHA-256 hashed before they leave
the browser, `?redirect=` validated, forgot-password never reveals an account, `LTNS_0023` leads to
`/auth/verify-email`, the setup form hidden while `httpInitEnabled === false`. ng-base implements the calls:

```ts
protected readonly auth = inject(LtAuthService);   // from '@lenne.tech/ng-base/auth'
await this.auth.signIn.email({ email, password });
this.auth.user();                                  // signal
await this.auth.twoFactor.verifyTotp({ code });    // sets the user on success
await this.auth.authenticateWithPasskey();
```

## Bug Reporter (bug.lt)

ng-base carries the Angular counterpart of `@lenne.tech/bug.lt`; there is no separate package to install.

- **`app.config.ts`:** `provideLtBug(options?)` from `@lenne.tech/ng-base/bug/provide`, the light entry. Never import
  `@lenne.tech/ng-base/bug` there: it would pull the reporter into the initial bundle of every visitor.
- **Shell:** `LtBugReport` from `@lenne.tech/ng-base/bug` in its `imports`,
  `protected readonly bugActive = inject(LT_BUG_ACTIVE);` (from `…/bug/provide`) and in its template
  `@if (bugActive) { @defer (on immediate) { <lt-bug-report /> } }`. `<lt-bug-report>` starts the capture when it is
  created, so production never loads it. Styles: `theme.css` includes them; next to `core.css`, as in ng-base-starter,
  add `@import '@lenne.tech/ng-base/ui/styles/components/lt-bug-report.css';` to `src/styles.css` (vendored app:
  `./core/ui/styles/components/lt-bug-report.css`). Screenshots need the optional peer `modern-screenshot`; without
  it the report goes out without one.
- **From code:** `LtBugReportService` from `@lenne.tech/ng-base/bug`: `open()`, `reportError(error, source?)`,
  `submit(report)`.
- **Server:** `ltBugReport()` from `@lenne.tech/ng-base/bug/server` answers `POST /_bug-lt/report` and files a
  Linear issue. Register it in `src/server.ts` before `express.json()` (whose 100 kB default rejects large reports)
  and before the Angular handler. The Linear credentials exist only on the server: `NG_LINEAR_API_KEY`,
  `NG_LINEAR_TEAM_NAME`, `NG_LINEAR_PROJECT_NAME`, never as `NG_PUBLIC_*`.
- **Active or not, decided at runtime, so one build serves every stage:** `NG_PUBLIC_LT_BUG_ENABLED` wins on both
  sides (per side: `enabled` in `provideLtBug()` or `ltBugReport()`). Otherwise `NG_PUBLIC_APP_ENV` `production` (or
  `prod`) switches it off and any other stage label on. Without a label both fail closed: the browser part runs only
  in dev mode, while the endpoint answers 404 even locally, so set `NG_PUBLIC_APP_ENV=local` for `ng serve`. Further
  browser options per stage: `NG_PUBLIC_LT_BUG_AUTO_SHOW`, `…_AUTO_OPEN_ON_ERROR`, `…_ENABLE_SCREENSHOT`,
  `…_POSITION`, `…_BUTTON_COLOR`, `…_BUTTON_TEXT`.

## Tests

Test-first (`building-stories-with-tdd`). Component and service specs next to the code (`*.spec.ts`, `ng test`
with Vitest); tooling and contract tests in `tests/unit/`; Playwright E2E against a real nest-server-starter, with
the helpers from `@lenne.tech/ng-base/testing` (`gotoAndWaitForHydration()`, `fillInput()`, `generateTestUser()`,
`generateTOTP()`, `createTestUser()`, `loginTestUser()`). E2E runs set an explicit `NODE_ENV` with a block in the API's
`src/config.env.ts` (`e2e`). Locally run the new and affected specs (`lt dev test -- <spec>`); the full suite runs
in CI.
