`lt-dev` works with tickets from [Linear](https://linear.app/). The Linear MCP server ships with the plugin; on first
use it signs you in through the browser.

## Where to start the session

Start Claude Code in the directory that matches the scope of the ticket:

| Directory | Use case |
|---|---|
| Project root | Changes in backend and frontend |
| `projects/app` | Frontend only |
| `projects/api` | Backend only |

## In one command: `ticket-cycle`

```text
/lt-dev:ticket-cycle            # pick the next ticket
/lt-dev:ticket-cycle DEV-123    # take this ticket
```

The command runs the whole cycle and stops only where your decision is needed:

1. **Take the ticket.** Without an ID it picks the next ticket in Fix needed or Open, by priority, never one that is
   assigned to someone else. Backlog is never picked. It sets the ticket to In Progress and creates a branch.
2. **Settle the decisions.** Claude looks up what the code, the ticket and the ADRs already answer, and asks you
   about everything that stays unclear or contradictory, each question with options and a recommendation. Nothing is
   built on a guess.
3. **Implement test-driven.** The tests come first, then the implementation until all tests and `check` pass.
4. **Review** (optional). `/lt-dev:review` fixes proven Critical and High defects.
5. **Check in the browser.** Claude starts the app with `lt dev up`, seeds test data and walks the changes.
6. **Your approval.** You get a test package with the steps and links and approve the change.
7. **Ship.** MR/PR, CI, merge (or a handoff to a reviewer), and the Linear comment with test steps for QA.

`--autopilot` runs the same cycle without questions (see [Unattended runs](./2.unattended-runs.md)).

## Step by step

When you only need part of the cycle, use the commands directly:

| Step | Command |
|---|---|
| Create a ticket | `/lt-dev:create-story`, `/lt-dev:create-task`, `/lt-dev:create-bug` |
| Implement and test | `/lt-dev:take-ticket` or `/lt-dev:resolve-ticket DEV-123` |
| Review | `/lt-dev:review` |
| Hand off to a reviewer | `/lt-dev:dev-submit` |
| Land the branch | `/lt-dev:git:ship` |

New tickets go to Open, not Backlog, unless you ask for another status: the automatic pick never takes a Backlog
ticket. Before a ticket is created, the team is searched for one that already covers it.

## A story without a ticket

You can also hand Claude a story directly:

```text
Implement the following user story with TDD:

As a <user type>
I want <functionality>
So that <benefit>

Acceptance criteria:
- <criterion 1>
- <criterion 2>
```

## Before you merge

All generated code is reviewed by the responsible developer before it is merged. Check every change for:

- **Correctness:** the logic matches the ticket, every acceptance criterion is met, edge cases are handled.
- **Security:** no injection (SQL, command, XSS), inputs are validated, permissions (`@Roles`, `@Restricted`) are
  correct, sensitive data stays protected.
- **Performance:** no N+1 queries, indexes where queries need them, no needless work in loops.
- **Code quality:** the project's conventions, clear names, sensible error handling, nothing more complex than
  needed.
- **Tests:** meaningful, with edge cases, readable.

If something is wrong, tell Claude in the same session what and why, and let it fix the code and the tests together.

## Good habits

- Keep one session on one ticket.
- Run the tests locally before you approve.
- Ask Claude to explain code you do not understand, and do not merge it until you do.
- Do not assume generated tests are complete: check what they leave out.
- Never ignore a failing test.
