## `/loop` with `--autopilot`

```text
/loop /lt-dev:ticket-cycle --autopilot --project=<Linear project> --team=<Linear team>
```

`--autopilot` runs the whole [ticket cycle](./1.ticket-workflow.md) without a single question, so `/loop` (without
an interval, self-paced) works a project ticket by ticket while nobody is at the screen. Starting it is your standing
approval for its defaults: the decision round settles every open point by its recommendation and posts the decisions
comment, the run reviews, walks the browser, attaches the test package to the ticket as a document, merges after a
green pipeline and verifies the dev deploy. Tickets of other repositories are skipped. A Blocked ticket is taken
once its blockers are Done or merged into the base branch.

- **Parked:** what no default can settle. The work is pushed to its branch, the ticket gets a comment with the
  question and Claude's recommendation, goes to Blocked and is assigned to you.
- **Halted:** a problem of the environment, such as expired access, a dirty base branch, Docker or an MCP server
  down, or the same cause twice in a row. The loop stops instead of parking ticket after ticket.

Each run ends with an `AUTOPILOT-RESULT:` line; `AUTOPILOT: NOTHING-LEFT` and `AUTOPILOT: HALT <reason>` end the
loop.

The autopilot never publishes content, never promotes `dev` into a higher branch, never sets a ticket to Done and
never bypasses a hook or a gate. The full list of questions and their defaults is in
[`commands/ticket-cycle.md`](https://github.com/lenneTech/claude-code/blob/main/plugins/lt-dev/commands/ticket-cycle.md),
section "Autopilot".

## A whole project in one run: `ticket-batch`

```text
/lt-dev:ticket-batch [<Linear project>]
```

Works every ticket of the project that is in Open or Fix needed and yours or unassigned, each through
`ticket-cycle`. Without a project it takes the one of the current repository.

1. **All questions first.** One `ticket-analyst` per ticket prepares the relevance check, the ADR check and a
   decision brief for every open point, read-only and in parallel. You settle everything in a few rounds, including
   the review and the Linear status after the merge.
2. **Build without questions.** The tickets are built one after another, each on top of the one before it, so the
   last branch is exactly what you test and what lands. A question that comes up during the build is set aside and
   asked in one round before the test.
3. **One test, one approval.** You get one test package for all tickets on a prepared stack and approve once.
4. **Merge in order.** Each merge request carries only its own commits, followed by one deploy check.

Content work and tickets of other repositories stay out, and the state of the run survives a `/clear`.
